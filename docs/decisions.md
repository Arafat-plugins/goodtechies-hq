# Decisions log

This file records decisions taken where the spec or the master prompt was silent, or where the
build had to deviate from them. Each entry has a one-line reason. The same entries appear in
`PROGRESS.md` → the "Decisions made in Phase N" section for that phase.

## Phase 0.5 (20 Sep 2026) — Design Foundation

Spec: `docs/design-foundation-v1.md` (v1.1). Brand source of truth:
`docs/design-refs/GoodTechies siteicon  1.svg`, which holds exactly three colours and no
gradient — `#0A0D12` (tile), `#FFFFFF` (glyphs), `#F04E27` (one dot). Token implementation:
`resources/css/app.css`.

**A note on the numbering.** The spec's §7 reserved `0.5-1` … `0.5-7` for the seven decisions
the phase had to *close*. T1 was written first and reused those numbers for its token choices,
so four of them meant two different things at once. The reserved numbers win, because the code
cites them with the spec's meaning (`app.css:75` → 0.5-1, `navigation/types.ts:39` → 0.5-3,
`app.css:57` → 0.5-4, `TimerHeroCard.vue:9` → 0.5-5). T1's seven colliding rows moved to
**0.5-21 … 0.5-27**, in their original order and with their original wording. Nothing was
deleted and no number now means two things.

## Phase 2 (20 Sep 2026) — Tasks

| # | Decision | Reason |
| --- | --- | --- |
| 2-1 | Phase 0.5's design foundation is accepted as-is and Phase 2 builds on it unchanged | The user ran it on their own machine and approved it before any Phase 2 screen existed. Changing a token now costs one task; after ten screens it costs ten |
| 2-2 | Files go to the **local disk** behind signed, expiring URLs, not S3 — `FileService` and its tests are written against Laravel's `Storage` abstraction so the move is a `FILESYSTEM_DISK` change in `.env` | The user chose it. The spec calls for S3, but no bucket exists yet and the signing, validation, metadata and version-history behaviour is identical either way. The tests assert the behaviour, not the driver |
| 2-3 | Phase 2 runs to its gate without intermediate check-ins, as Phase 0.5 did | The user chose it |
| 2-4 | `BACKLOG` and `CHANGES REQUESTED` get their own status token sets (hues 196 and 344) rather than being mapped onto an existing tone | The spec has eight statuses; Phase 0.5 drew six before that list existed. A board where BACKLOG and TO DO are the same colour is a board that lies. Both new pairs measured over 4.5:1 in each theme, and both survive a deuteranope simulation against the existing six |
| 2-5 | **Follow-up, not fixed:** `review` (hue 75) and `waiting` (hue 50) are deltaE 0.16 apart under deuteranopia in light mode — effectively one colour to a red-green colourblind viewer | Found while placing the two new hues. It predates Phase 2 and re-tuning a shipped token is not this slice's business. It is survivable only because `StatusBadge` always prints the label, which is the evidence for the "colour is never the only carrier" rule rather than an exception to it. Worth its own brief |
| 2-6 | The employee Tasks table drops the Assignee column; the admin one keeps it | `Task::visibleTo()` already scopes an employee to their own tasks, so the column would print the reader's own name on every row. It is also why the employee surface offers no group-by-assignee: it would produce exactly one group |
| 2-7 | Grouped lists open from the top until ~15 rows are showing, then collapse the rest with counts | Eight expanded status groups is a wall and eight collapsed ones is a list that shows no list. The rule is a constant inside `DataTable`, not a per-screen prop, so Board and Calendar inherit the same answer instead of each inventing one |
| 2-8 | **Follow-up:** the Tasks list has no Assignee filter, because neither controller sends an employee list to build the picker from | `TaskService` already accepts `assignee_id`; only the props are missing. Shipping the control with an empty option list would be the "lie in the UI" that 0.5-19 forbids. Slice 2 adds the prop and the filter together |
| 2-9 | A task's `status` is guarded at the **model**: `Task` throws if `status` is dirty on an existing row and the write did not come through `applyTransition()` | The plan requires that every drag use the same checks as the form. A shared route is only intent — a future job, command or controller could still fill `status` from input. The guard makes the single path structural, and `applyTransition()` re-checks the transition map, so no path reaches an illegal status |
| 2-10 | "Explicit hand-off" is a recorded promotion of the other assignee to primary, with a required reason, audited as `task.reassigned`. The current primary may do it without a manager | The plan names hand-off without defining it. Storing the summary's author reduces completion to one question — is `work_summary_by` the primary's user — and the hand-off is the only thing that moves the subject of that rule. A primary handing their own work over before leave is the case it exists for; needing a manager would leave the task uncompletable until Monday |
| 2-11 | The original completion lives in columns on `tasks` (`first_completed_at`, `first_completed_by`, `first_work_summary`), not in the activity log | `activity_logs` carries a description string and nothing else, so the first completion could only survive there as prose — unqueryable, and "how many tasks were completed late and then reopened" becomes a string search. A log is what happened; the row is what is true. Reopen clears the live `completed_at`, since a row claiming a completion date while In progress contradicts itself |
| 2-12 | DESIGN.md §5.19 ("nothing routes a flash through the toaster") gains a sanctioned exception: a screen whose every write is a server round trip may claim the channel with `useFlashAsToast()`, which **moves** the flash rather than copying it | The task detail answers every write — including a refused transition — with `back()->with()`. The rule's intent is "announce once", not "never as a toast", and the collision was real: the first run showed the alert and the toast saying the same thing |
| 2-13 | The assignee list is filtered by holding `tasks.view`, not by role name or an exclusion list | The Accountant was being offered as an assignee for tasks they cannot open. A permission check means a future role that can carry tasks appears with no code change, and one that cannot never does — verified by moving the permission in both directions |
| 2-14 | The Tasks list tag filter shows globals plus the tags of every project `Project::visibleTo()` returns; a single task's picker shows only its own project's plus globals | Two different questions. The filter must cover every label a visible row could wear, or it hides work the list is showing; the picker must cover only what may legally go on that task. Sending every tag — which is what `index()` did — leaked other clients' project vocabulary through tag names on the Employee surface |
| 2-15 | **Follow-up:** a cross-project move drops the task's foreign *tags* but leaves its *dependencies*, so a moved task can still be blocked by a task in its former project | `addDependency()` refuses a cross-project pair, so the move can produce a state the validation exists to prevent. Found while building the move dialog; it needs a decision about whether the move detaches them, refuses, or warns |
| 2-16 | The Calendar's date window is an **interval overlap** — `coalesce(due_date, start_date) >= from AND coalesce(start_date, due_date) <= to` — not `whereBetween('due_date', …)` | A calendar draws a span, not a point. A task starting 28 Aug and due 3 Sep is being worked on at both ends and belongs on both grids; `whereBetween` on August drops it entirely, so the bar that should run off the right edge simply is not there. The `coalesce` also turns a task with one date into a single day rather than a NULL no comparison matches |
| 2-17 | Board and Calendar are **separate routes**, not a `?view=` parameter on the index | Each is bookmarkable, and each gets its own row in the permission matrix. A query-string variant would share one row and hide a surface from the route-coverage guard |
| 2-18 | A Board lane orders by `position` first; the List keeps ordering by due date. The ordering is a named parameter on `TaskService::query()`, not a fact about it | Two views, two questions. A list read top to bottom wants the soonest work first; a lane you drag wants the order you dragged it into. The Board originally reused the List's ordering, which put `position` third behind a date where it almost never broke a tie — so a card dropped at the top sprang back, and a manual order that does not visibly hold is worse than none |
| 2-19 | A lane is a **status**, not a `(project, status)` pair: `position` is scoped per status and a card may be reordered against one from any project | The plan's Board is "columns = statuses" across every project, and a card shows its project name because the lane mixes them. Per-project scoping meant a card could only be reordered against its own project's cards, and the screen had to walk a drop anchor backwards to find one — a workaround for a model that did not match the picture |
| 2-20 | **Follow-up:** `TaskResource::permissions()` resolves `can_review` per row, and `TaskPolicy::review()` resolves the reviewer per task — a query per card on the List, Board and Calendar | Inherited from slice 1 and harmless at 25 tasks. It is the thing that will bite first when a real board has hundreds. Wants a batched reviewer lookup, not a per-row gate call |
| 2-21 | **Follow-up:** an Admin board card carries the whole project fragment — client, internal notes, billing type, contract terms, finance — on every card, to print a project name | Correct privacy and correct `ProjectResource` behaviour, not a leak: an Admin may see all of it. But it is a lot of payload for one line of text, and finance detail sits in the browser on a view that never shows it |

| 2-22 | A tag's colour is the *name* of a status token (`backlog`…`cancelled`), not a hex value — enum, `Rule::enum`, and a CHECK constraint generated from the enum, with the picker's options sent from the server | Three places could hold the list: the enum, the constraint, and a Vue array. The third is the one that drifts, so there is no third — `GET …/tags` ships `colours`, and `statusToneClass()` turns a name into the triplet the rest of the app already uses. It also means a tag cannot wear a colour the design system has no token for |
| 2-23 | Deleting a tag writes the audit row **before** the cascade, while the pivot still exists | `task_tags` is gone by the time the delete returns, so the count of what it came off can only be taken first. An audit row saying "deleted" without saying what it cost is the kind of record you only notice is useless the day you need it |
| 2-24 | A conversation's membership is **computed**: `ConversationPolicy` asks the linked task's `TaskPolicy::view`, and `conversation_members` holds read state only | A stored member list is a second permission model that drifts from the first — reassign a task and the old assignee's row still says "member". A test reassigns a task and asserts the stale row buys nothing. `last_read_at` is the only thing the table is for |
| 2-25 | A file's signed `url` is a **policy check**, not a bearer token: `URL::temporarySignedRoute` into the app, never `Storage::temporaryUrl()`, and `local.serve` is turned off | A signature proves the link is untampered; it says nothing about who is holding it. Forwarding a signed bucket URL hands over the bytes. This way `FilePolicy::view` runs on every fetch, so a forwarded link is 404 for someone who may not see the owning record. `'serve' => false` removes Laravel's own bearer `GET /storage/{path}` route, which was unreachable but one `Storage::url()` call away from not being |
| 2-26 | `FileResource`'s `versions` key and `File::versions()` are **deleted**, and history is its own endpoint | `version_of` holds the root's id, so the relation hangs the chain off v1 — and `for()` returns only current rows, so the root is never in the list the moment a replacement exists. The key answered `[]` for every row a caller could hold, which meant replacing a file quietly buried every earlier version. A relation that is empty exactly when it matters is the trap that produced the bug, so it is gone rather than re-documented; `FileService::history()` reads the chain through `chainId()` and `GET {surface}/files/{file}/versions` serves it |
| 2-27 | `UpdateTagRequest` checks visibility in `authorize()`, ahead of its own rules | `rules()` builds the uniqueness scope from the routed tag, and a Form Request validates before the controller body — so a PUT naming a tag scoped to an invisible project answered 422 ("already exists in this scope") where `visibleTag()` would have said 404. | 2-41 | The Notification Center is the **same route** that answers the bell's JSON: `GET /notifications` renders the page for a browser and the identical array for a fetch | A second route rendering a page that then fetched this one would have meant another controller method, another matrix row, and two owners of "which tab am I on" — the tab is a bookmarkable query parameter, and a page re-reading it client-side would hold it twice |
| 2-42 | **Follow-up:** the Accountant costs one `403 /notifications/recent` per full page load before the bell removes itself | Deliberate — deciding it in Vue would mean naming a role, which is exactly what `NotificationPolicy` refuses to do. Avoidable by sharing the mailbox permission in `HandleInertiaRequests`, which would change every page's prop shape and the tests that assert it |
| 2-43 | **Follow-up:** `Pagination.vue` draws Laravel's `…` ellipsis entry as a filled, active-looking pill | It filters on `link.page !== null` and the ellipsis row has no `page` key at all, so `undefined !== null` lets it through. | 2-44 | **Follow-up:** `relativeTime()` now exists in four places | Two project/client screens, the sessions card, and `notifications.ts`. | 2-45 | `TaskCompleted` notifies the **assignees** as well as `created_by` and the reviewer, widening the spec's own recipient list | The plan contradicts itself: the Phase 2 Backend paragraph lists `created_by` + reviewer, and the same phase's "Done when" says a notification appears at every step. On this team those two people are usually one person who is also the actor — and the actor is always dropped — so an approval wrote **zero** rows and the person who did the work was never told it was accepted. The acceptance sentence wins, because it is what "done" means; the list reads as an implementation note written before anybody walked the flow. Nobody learns anything they could not already see by opening the task |
| 2-46 | `TaskSubmittedForReview` has a plural branch: a resubmission reads *"…is waiting for your review **again**"* | A second submission groups into the reviewer's existing unread row (2-33), so without one the sentence still described the first submission and the only sign anything had changed was `count`, which the screen deliberately does not print. ## Phase 3 — recurring tasks

| # | Decision | Reason |
| --- | --- | --- |
| 3-1 | The **partial unique index** `(recurring_task_id, recurring_period) where recurring_task_id is not null` is the duplicate prevention; the engine's check is only the nice error | Two schedulers, a retried queue job and a manual "Generate now" on the same minute must not produce two October tasks, and an `if` cannot promise that. `TaskService::create()` writes both columns in the same INSERT as the task (a create-only `BIRTH_FIELDS`, so an update cannot restamp a period), so there is no window between the check and the row. A test writes the competing row from a `Task::creating` listener — strictly after the check, strictly before the INSERT — and asserts the message only reachable from the catch block |
| 3-2 | The index deliberately does **not** exclude `deleted_at` | A soft-deleted instance still occupies its period. Excluding it would let tomorrow's 00:05 run resurrect a task somebody deleted on purpose. `instanceFor()` uses `withTrashed()` so the check and the index agree exactly |
| 3-3 | A period key is one function with one `match`: `2026-10`, `2026-W41`, `2026-10-07` | Two properties carry weight and are tested: a key is unique within one template (a template has one frequency, so its keys are all one shape), and keys of one shape sort lexicographically into chronological order — which is why "is last period's instance still open" is a plain `where recurring_period < ?` and not a second date column. The weekly key uses the ISO year, so 29 Dec 2025 is `2026-W01` rather than sorting a year out of place |
| 3-4 | **"Ended" means the project's status is no longer open** — Completed, Cancelled or Archived. On Hold keeps generating, and a passed `deadline` is not ended | The spec's stop list never names On Hold, which means "paused and coming back". And every seeded retainer carries a rolling deadline a few days out, so treating a slipped date as the end would silently stop every retainer in the agency inside a week. The stop is derived on every run rather than flipping `active` off, so unarchiving a project resumes it by itself |
| 3-5 | Generating a task adds **no** new notification type | `TaskService::create()` already fires `TaskAssigned`. A second row for the same act would break §11's "one event = one notification" |
| 3-6 | A migration rewrites the `notifications_type_is_known` CHECK from the enum whenever a phase adds a type | Phase 2 generated that constraint at create time, so a Phase-2-era database would have refused the first due-tomorrow reminder at 08:00 the morning after deploy while every test passed. **This is a trap that will be stepped in again** — every future phase adding a notification type needs the same migration |
| 3-7 | **Follow-up:** `hq:notify-due-tomorrow` dedups "ever", not per due date | A task moved from Friday to Monday is "due tomorrow" a second time and gets no second reminder. It is the same trade `hq:flag-overdue` already makes, mirrored on purpose rather than inventing a second dedup rule — but it is a real limitation |
| 3-8 | The recurring screens are **Admin-only**, and every non-Admin cell in the matrix is **403**; **404** is reserved for the record | A Manager owns the tasks a template produces, but a standing monthly instruction is a decision about the engagement, not about this week's work. The refusal is about what they may do, not which shell they arrived in — `surface:admin` and `RecurringTaskPolicy` both say no. The 404 branch re-resolves every per-template lookup through `RecurringTask::visibleTo()` *before* the policy, so a template on an invisible project is absent; no matrix row can show it today, because an Admin sees every project, so it is asserted directly instead |
| 3-9 | The recurrence editor sends `frequency` plus that frequency's parameters; one server-side `match` picks one of `RecurrenceRule`'s three constructors | Nothing in the Vue does month arithmetic, ISO weeks or day counting — the next run, its period, the period's bounds and the due date all come back from a preview endpoint, which is `RecurrenceRule` answering. The unused frequencies' values ride along and are ignored, so toggling the editor twice is not a validation error |
| 3-10 | The form re-states the rule's bounds instead of relying on it | `RecurrenceRule` *clamps* an out-of-range day, which is right for a command running at 00:05 and wrong for a form: somebody typing 31 would silently get 28 |
| 3-11 | `RecurringTaskEngine::stopReason()` became public | The screen asks the same method the 00:05 run asks. The alternative was a second copy of the plan's §21 stop rules in a controller, or a screen that prints only the last log row's message — which says nothing at all for a template whose project was cancelled this morning |
| 3-12 | **Follow-up:** a template can be switched off but not deleted | The spec names an active toggle and no delete, so one set up by mistake stays on the list forever. Worth a client decision |
| 3-13 | **Follow-up:** a template's name on task detail still carries its placeholder — "Buffalo Modular Monthly SEO — {period}" | Correct, since that *is* the title pattern, but it reads oddly beside the rendered title. The alternative is inventing a second "display name" field, which is a decision rather than a fix |


| 2-52 | **Resolved is a separate column from read.** `notifications.resolved_at` is new; `is_read` is untouched | They mean different things and mixing them would have broken 2-33. `is_read` means *you looked* and closes the group; `resolved_at` means *you dealt with it* and only quietens the row. Collapsing them would have closed the group too, so a resubmission would have started a fresh row of one and told the reviewer, for the second time, exactly what it told them the first — which is the bug 2-46 exists to prevent. Growing a row clears `resolved_at`, so the resubmission re-enters the badge |
| 2-53 | What resolves a notification is a fact about the **type**, listed beside `priority()` and `tab()`, and only the **actor's own** rows resolve | `TaskSubmittedForReview` is answered by either review verdict; nothing answers `TaskCommented` — reading a comment is not answering it. And two admins can both be reviewers, so one ruling must not empty the other's bell: they have not read it. The rule is applied in `NotificationService` *before* the empty-recipient return, because on this team the approver is usually also the only recipient, so his approval writes zero rows — resolving hung off a row being written would have missed the exact flow 2-48 was raised about |
| 2-54 | The reviewer's reason reaches the singular sentence only, whitespace collapsed and capped at 120 characters | A grouped row stands for several moves and cannot carry several reasons; printing the last one would attach it to a sentence about all of them. The cap is about what gets pushed out of view, not about the layout breaking — measured at 360px, a 500-character reason makes a 360px-tall row in a popover that shows ten |
| 2-55 | **Follow-up:** an assignee moving a task back out of review leaves the reviewer's row open | *In review → In progress* is a legal move for the assignee, so the review request is moot — but the actor is not the reviewer, and 2-53 says one person's act may not empty another's bell. Closing it needs a rule about the **object's state** rather than about who acted, which is a different shape |


## Phase 4 — time and attendance

| # | Decision | Reason |
| --- | --- | --- |
| 4-1 | `time_entries` has **no `state` column**: running, paused and stopped are read off the two timestamps that cause them | A `state` string would be a second statement of the same three predicates (2-37), and it would first disagree with them the day a watchdog stop forgot to keep them in step. The scopes are the single spelling, and the partial unique index is written against the same predicate |
| 4-2 | **One open timer per employee is a partial unique index**, `where ended_at is null`, with paused counting as open | The widget, a replayed offline batch and the watchdog can all reach the same employee in the same millisecond, so an `if` cannot promise it. The check above it exists only to produce a readable sentence. Paused counts as open because a second session beside a paused one is how an afternoon gets counted twice. Same reasoning as 3-1 |
| 4-3 | On replay, **only the heartbeats are evidence**, and nothing in the service increments | Every write sets `ended_at`, `paused_seconds` and `duration_seconds` to absolute values computed from timestamps, so the same batch landing five times leaves the row in the same state five times. The entry never ends later than the last heartbeat, which is what "server wins" means in practice: a client claiming six hours with nothing after 13:04 to show for it gets 13:04 |
| 4-4 | The watchdog's **rule 2 fires only on unflagged entries** | Otherwise it fires again a minute after the employee resumes, and a safeguard that cannot be acknowledged is one people route around. The flag stands; the rule does not repeat |
| 4-5 | Rule 1 runs before rule 2 | An entry both silent and overlong is a closed laptop, and the true account of a closed laptop ends at its last check-in, not at the maximum session length |
| 4-6 | A timer flag is a **sentence carrying its threshold and its moment**, not a code | "Stopped automatically: the timer stopped checking in for more than 5 minutes, so this entry ends at its last check-in, 1:04 pm." A flag nobody can read is a flag nobody investigates |
| 4-7 | Totals ask exactly one question: `approved_at is not null` | An auto entry is approved by the system at stop; a manual one only when `manual_time_requires_approval` is off. One nullable timestamp, no status enum that can contradict it. **Pending hours are reported separately and in words** so that nothing a person actually worked is invisible while it waits |
| 4-8 | `tasks.tracked_seconds` became a **recomputed cache**, never incremented | It is refreshed from `time_entries` on every stop, manual entry and edit. Phase 2's seeder wrote fabricated figures onto about twenty tasks, so the first real session on one of them visibly replaces the fabrication with the truth — correct, and worth knowing before it surprises somebody at a demo |
| 4-9 | `attendance_records` is unique on `(employee_id, date)`, and **Off Day and Remote are not storable statuses** | Three writers reach the table and one of them is an unattended 23:55 sweep, so check-then-insert is not a promise anyone can keep. | 4-10 | An employee with **no `start_time` cannot be Late** | Lateness is a comparison against a scheduled start. Where there is none, the honest answer is Present, not a default hour invented by the system |
| 4-11 | **Tapu can never be marked Absent**, and that is structural rather than a matter of discipline | Both the policy and the service require `tracking_mode = office_attendance` before a row can be written, so no hand — Admin, command or seeder — can write one. | 4-12 | Phase 5's leave/holiday skip plugs into **one method**, `coveredByLeaveOrHoliday(Employee, date)`, which returns false today | Called from exactly one place in `markAbsent()`. | 4-13 | The attendance **month grid becomes a list below `md`** | Measured, not stylistic: seven columns at 360px gives about 48px of cell, and every status here must print its **word** — DESIGN.md §2.2 measures four of eight status tones failing 3:1 in light without the label, and §1.4 has a deuteran pair at ΔE 0.16. "Half day" does not fit in 48px at any legal type size, so a phone grid would have had to drop the word or the date |
| 4-14 | `attendance.edited` and `schedule.changed` were added to the audit events, although Part C §4's list names neither | Treated as an omission rather than a decision: an attendance row is what Phase 9 pays from, and a schedule change silently relabels a fortnight of past arrivals as late or on time. `time_entry.edited` logs **every** edit, not only an Admin's — a trail that depended on who was signed in would be the wrong trail |
| 4-15 | Clocking in lives in `routes/shared.php`, not per surface | Part D §8 is explicit that both Admins clock in too, so it is a fact about the person rather than the shell they are in — the same reasoning as the profile and the file download. It also meant `routes/employee.php` needed no change, which is one fewer contested file between two concurrent agents |
| 4-16 | **Follow-up, and the one that will bite at GATE C:** there is nowhere to approve a pending time entry | `manual_time_requires_approval` defaults on, so a manual or edited entry is written unapproved and does not count. The only screen that could sign it off is Admin → Workforce → Time, which is the next slice. Until then those hours are reported in words but genuinely uncounted |
| 4-17 | **Follow-up:** `tests/Unit/SurfaceTest.php` asserts a hard-coded count of audit-event cases | Every phase that adds an event must bump it, and two concurrent agents both had to this round. Brittle, and it should assert the set rather than the size |
| 4-18 | Rejecting a time entry **keeps the row, its hours and the employee's own reason**, and adds `rejected_at`, `rejected_by`, `rejection_reason` with a CHECK that approved and rejected cannot both be set | A refusal that deleted the row would leave the person who recorded the hours with no trace of what happened to them. ## Phase 5 — leave and holidays

| # | Decision | Reason |
| --- | --- | --- |
| 5-1 | A **holiday is derived, never stored**: `holiday` was removed from `AttendanceStatus::storable()` and the CHECK rewritten from the enum | Decision 4-9's rule applied a third time. A stored Holiday would outlive the calendar it was copied from, so adding or removing one must change what a *past* day shows — there is a test that adds one, asserts the change, deletes it and asserts it back. `Leave` deliberately stayed storable: it records a decision about a person, not a fact derived from a shared calendar |

| 5-6 | `leave_types` has **two** booleans — `has_balance` (capped) and `is_unpaid` (costs pay) — not one | They coincide only on Unpaid. **Other is uncapped and still paid**, so a single flag read as "uncapped means unpaid" would have docked a day of Other leave and nothing would have said so until a payslip did |

| 5-9 | Approving leave for a **remote-timer employee writes no attendance row at all** | Decision 4-11 held rather than worked around: an approval quietly becoming the one hand that can write Tapu a row would take "Tapu is never Absent" apart from the inside. His balance, `unpaid_days`, calendar, task flag and sweep-skip all work identically |
| 5-10 | On approval, a day whose row has **no clock-in** is claimed; a day somebody clocked into is left alone | The first is the Absent the 23:55 sweep wrote, which a retro-approval should correct. The second is evidence that a person was at work, and leave does not erase it |
| 5-11 | The "assignee on leave" flag is **one `addSelect` in `TaskService::query()`** — the single funnel for List, Board, Calendar, My Tasks and the dashboards | Every view gets it with no extra query (asserted: a full task list is still one select on `tasks`). | 5-12 | Leave lives in `routes/shared.php`; the Accountant applies in their own shell | Part C §1 gives *apply for own leave* to every role. Decision 4-15's shape exactly, and it left `routes/employee.php` and `routes/accountant.php` untouched — one fewer contested file between two concurrent agents |
| 5-13 | The leave calendar becomes a **list of the days somebody is away** below `md` | Measured: a seven-column cell is 40px at 360 against the 184px the row's badge wants. Decision 4-13's attendance cell had ~48px and could not fit one status word; a leave cell must fit a name *and* a word. The list also skips empty days, which a grid cannot |
| 5-14 | **The Accountant now has a mailbox**, and nothing was carved out to give them one | `leave.apply` is a key Part C gives every role, so `NotificationPolicy::viewAny` simply stops refusing them. | 6-20 | **A voice note's accepted types are their own narrow list** — `FileService::VOICE_TYPES`, reached only when the caller passes `AttachmentKind::Voice`. `TYPES` is byte-for-byte unchanged | Putting audio in `TYPES` would widen the upload allow-list for **every** file panel in the application — tasks, projects, clients — which is a far larger blast radius than this feature needs. Audio is uploadable as a voice note and nowhere else. Two tests guard it, and merging the lists fails both: an audio file through the Files panel is 422, and the **same bytes to the same message endpoint without the word `kind`** is 422 — which shows the narrowing is the kind and not the route |
| 6-21 | **An audio-only WebM is `video/webm` to finfo**, and this was measured rather than assumed | `assertAcceptable()` reads Symfony's finfo guess over the temp file's bytes, not the client's claim, and finfo names the **container**: a WebM with no video track is still a WebM, and an audio-only MP4 is `video/mp4`. | 6-22 | **`voice` is the only kind a client may assert** | `file` and `image` are derived from the file itself, and a client that could claim one would be a client deciding whether its own upload renders inline in everybody else's thread. `voice` cannot be derived — no MIME type tells a recording from an attached audio file — so it is the one word the composer sends and the one word the request accepts |
| 6-23 | **A recording is 1…300 seconds, refused at the boundary and clamped at the write** | The Form Request 422s anything outside the range and writes nothing — a person who sent something wrong is told, not silently corrected. `MessageService::voiceSeconds()` then clamps for callers that never meet a Form Request (a job, a console command, an importer), because a bad number in a batch should not become a failed batch. It also returns null for any kind that is not `Voice`, so a length can never attach itself to a PDF |
| 6-24 | **Hold-to-record and click-to-latch are the same button, split at 300 ms** | The plan asks for hold-to-record, which is unusable with a keyboard and hard with a motor impairment. `pointerdown` starts recording immediately — asking for the mic costs ~100 ms even when granted, so classifying the gesture first would eat the first word — and the release decides: ≥300 ms is a hold and stops; <300 ms is a click and latches, so the next press stops. A keyboard activation fires only `click`, so `Space`/`Enter` are always the toggle. **Both misreads are recoverable and neither sends anything:** a hold read as a click leaves you recording with a Stop in front of you, a click read as a hold gives you a one-second clip with a Discard beside it |
| 6-25 | **The mic control is not drawn at all** where `MediaRecorder` is missing or no container is supported | A control that cannot work is worse than no control. Secure-context detection uses `window.isSecureContext` — the browser's own rule — rather than a hostname list of ours, which would be wrong on whichever engine moved last |
| 6-26 | **The stream is released on all four exits** — stop, cancel, error, unmount — and released *before* the preview, not after sending | A mic light left on while somebody decides whether to send is the kind of thing that ends trust in an application. Proved by patching `MediaStreamTrack.prototype.stop` to count calls and asserting **both** a rising count and zero tracks still `live` — either alone can lie |
| 6-27 | **`VoicePlayer` takes no `onAccent` and draws no surface of its own** | `AttachmentCard` already declares `bg-card text-card-foreground` on its root, so a player inside a DM's brand bubble is on `--card` and not on the fill. | 6-28 | **Follow-up, and it is the one that matters:** the download route serves **no byte ranges**, so a sent voice note cannot be scrubbed | `FileService::download()` returns a `StreamedResponse`; `Range: bytes=0-99` comes back **200 with the whole file** and no `Accept-Ranges`. Measured: the recorder's own preview (a `blob:` URL) reports `seekable [[0, 2.4]]` and seeks perfectly; the same clip once sent reports `[[0, 0]]` and swallows every `currentTime` write. The player therefore **probes whether a seek actually landed** and, when it did not, disables the slider and renames it *"(this one cannot be moved through)"* — §5.11, never render a control the server ignores. It re-enables itself the day ranges are served, with no client change |
| 6-29 | **Follow-up:** a `MediaRecorder` WebM carries no duration or cues in its header | Which is why `audio.duration` is `Infinity`, why `duration_seconds` is load-bearing rather than a convenience, and why 6-28 is not fixed by ranges alone — a server-side remux (`ffmpeg -c copy`) would fix seeking properly |
| 6-30 | **Follow-up:** `MessageService::MAX_VOICE_SECONDS` and `voice.ts`'s `VOICE_MAX_SECONDS` are two copies of `300` and nothing enforces that they agree | They match today. If the rule moves, one moves alone, and the symptom is either a recorder that stops at the old ceiling or a 422 the UI said could not happen |
| 6-31 | **Follow-up:** `GET /messages/{conversation}` renders raw JSON to a browser navigation, **and marks the thread read while doing it** | `show()` is typed `JsonResponse` and always answers JSON; the page is `/messages?conversation=N`. | 6-32 | **Follow-up:** `<script setup>` top-level bindings are per-instance, not module scope | The "only one voice note plays at a time" registry was first written as a `let current` at the top of `VoicePlayer.vue`. It looked shared, was not, and two notes played at once. Moved into `voice.ts`. Worth checking anything else in this codebase with that shape |

## Phase 9 — Payroll (25 Sep 2026)

| # | Decision | Reason |
| --- | --- | --- |
| 9-1 | **Salary history is an effective-from row per change**, never an edit of an old one | The tempting alternative — one mutable current row, old values recoverable from `audit_logs` — fails the one requirement the table exists for: a payroll run must say **which salary it used**, and re-running an old month must give that month's number. `audit_logs` cannot answer it: ADMIN-only by Part C §1, shaped as JSON old/new, no index on the subject, no notion of *in force on this date*. Answering *"what did Tapu earn in September"* would mean folding every `salary.changed` row in order, inside a calculation, **on a table the Accountant who runs payroll may not read**. With effective-dated rows a November raise is arithmetically invisible to a September question and nothing has to remember to exclude it |
| 9-2 | **The daily rate is `(base + allowance) ÷ working days in the month, on that employee's own schedule`** | The divisor is working days because of what the **numerator** counts: `leave_requests.unpaid_days` is already working days on that person's `schedules.working_days`. Divide a monthly salary by 30 and the two sides stop describing the same thing — somebody who took **every** working day of September unpaid would be docked 22/30ths and paid for the other eight. With working days on both sides **the rule closes**: a whole month unpaid deducts a whole month's recurring pay, exactly, and there is a test called that. The divisor uses the **same predicate for the same person** that counted the days being deducted, so it cannot disagree with itself — including the documented asymmetry where somebody with no schedule row counts every day on **both** sides. The numerator includes the allowance because an allowance is monthly pay for the same month's presence; deducting from base alone would pay a full transport allowance for days nobody travelled |
| 9-3 | **`payroll_items.net_salary` is a PostgreSQL `GENERATED ALWAYS … STORED` column** | Part D §20 names it as a column, so a payslip that is issued and archived can be re-read without recomputing it from parts an Admin has since corrected. The question is therefore not *store or compute* but **who computes it**, and the answer that makes the two impossible to disagree is the database, on write. An item whose net does not match its parts cannot exist — not from the service, a seeder, a Phase 12 import, `psql`, or a future screen that updates `bonus` and forgets to recalculate. `numeric + numeric` is exact base-10, so no float appears; the one **division** in the feature is done in PHP in whole cents with integers only (`intdiv(2n + d, 2d)`, half up) and lands as an exact two-decimal figure before the generated expression sees it. A test asserts a raw `UPDATE … SET net_salary` is refused |
| 9-4 | **`net_salary` may be negative and is not clamped** | An advance larger than the month's pay, or a whole month unpaid plus an advance. That is what next month recovers; clamping at zero would quietly forgive money owed. Same reasoning as the finance rollup's negative net |
| 9-5 | **`payroll_periods` has no `locked_by`, `approved_by`, `approved_at` or `paid_at`** | Each is a fact `audit_logs` already holds with actor, timestamp and IP, in the one table `hq_app` can neither UPDATE nor DELETE. What the table does keep is `locked_at`, because a payslip quotes the moment the month closed — and two CHECKs keep it honest: `(status IN ('locked','paid')) = (locked_at IS NOT NULL)`, and `(lock_reversed_by IS NULL) = (lock_reversal_reason IS NULL)`, so a reversal with nobody attached or with no stated cause cannot exist |
| 9-6 | **The auto draft's idempotence is two unique indexes, not a column and not a lock** | `payroll_periods.month` UNIQUE and `payroll_items (period, employee)` UNIQUE — enforced against **every** writer rather than being a query the command has to remember to run. The period is re-read inside the transaction with `lockForUpdate()`, so two simultaneous runs cannot both decide the month is empty. A `drafted_at` column would be a second record of a fact the row's own existence states; a Redis lock is worse, because Redis is a cache here and a flush would let the next run draft the month **again** — and "again" means a second set of payslips for a month the Accountant may have started balancing. Same argument as 7-5, stronger |
| 9-7 | **A month that already has a period is never topped up**, whatever state it is in | A test walks September to Approved, adds a new employee with a salary backdated to the 1st, runs the command, and asserts the period is still Approved with no line for the joiner — and that even `updated_at` did not move |
| 9-8 | **The self-scope 404 comes from the query, not from a branch** | `findItemFor()` resolves **through the same scope** the listing uses, so there is no code path that could produce a 403 — and an id that matches nothing and an id belonging to somebody else give byte-identical responses. Part B §3 rule 1's three halves are three named tests: omission, the 404, and the audit row |
| 9-9 | **The restricted-access audit row is written only when the record exists and belongs to somebody else** | An id matching nothing is a typo or a stale bookmark, and logging those would bury the rows Part C §3 actually asks for in noise. Nothing about what is logged is observable from outside, because the response is identical either way. The row carries the item id and the subject's employee id and **not** `net_salary` or `base_salary`: an audit row about a **refused** read must not carry the figures the read was refused |
| 9-10 | **`admin_notes` goes to an ADMIN and to nobody else — not the Accountant, and not the employee it is about** | The Accountant is excluded in as many words (Part D §14, Part C §1). The employee is a decision this slice takes: Part C grants *"view own payslip"*, and a payslip is what was earned and deducted. `admin_notes` is what one Admin writes to another about somebody's pay — *"advance to be recovered next month"* — and Part C is deny-by-default. Sending it to the subject would also make the column useless for its stated purpose and push those sentences into a channel with no privacy rules at all. It is a **role** and not a key, because Part C §1 forbids inventing a key for a scope; the mechanism is a spread `['admin_notes' => …]` or `[]`, never `$this->when()`, which a later refactor into a merge would turn back into a `null` for exactly the people it is hidden from |

## Phase 10 — Search & Gantt (25 Sep 2026)

| # | Decision | Reason |
| --- | --- | --- |
| 10-1 | **A column is indexed for search only if EVERY viewer the row's scope admits may read it** — stricter than *"the searcher may read it"* | This is the invariant that makes the **count** safe for free: a hit can only ever be caused by text the matcher was already allowed to read. Excluded on that basis: `projects.internal_notes`, `clients.internal_notes`, `clients.contact_info`, any denormalised client name, and every money column. Snippet columns are always a subset of searchable ones, asserted per type |
| 10-2 | **Scope is a PREDICATE in the same `WHERE`, never a pre-materialised id list** — and the query plan proves the rule rather than working around it | Measured on 50 000 synthetic projects: the predicate form is **1.48 ms and keeps the GIN index**, with `Sort` and `Limit` sitting *above* the scope filter so only accessible rows ever reach ranking. The id-list form is **19.6 ms and abandons the index entirely**. "Scope before rank" is a statement about relational algebra — `WHERE` runs before `ORDER BY` — and does not require the scope to be the physical access path. **Nothing was traded.** The refactor that would silently undo both properties at once is materialising the scope, so the service docblock says so |
| 10-3 | **`simple`, not `english`** | `english` removes stop words, so a client genuinely called *The Gap* becomes unfindable **silently** — an empty result set looks exactly like "no such client" — and it stems proper nouns into each other. What `english` would have bought is bought back on the query side by prefix matching, which never drops a word |
| 10-4 | **`to_tsquery` over a hand-built string, not `websearch_to_tsquery`** | The safer function cannot prefix-match, and a palette that finds nothing until you finish the word is one nobody opens twice. `to_tsquery` throws on malformed input, so the safety rests on a whitelist: every character that is not a letter, digit, `.`, `_`, `-` or `@` becomes **a space, not nothing** (so `O'Brien` is two tokens matching the two lexemes the parser makes, rather than one matching neither). `buffalo modular` → `buffalo:* & modular:*`; `"home model"` → `home <-> model`, adjacent and unprefixed; a bare `@` or `& \| ! ( ) :` → **200 with nothing in it**; an unbalanced quote — which *every* quoted search passes through — searches the words it has |
| 10-5 | **The Accountant's restriction falls out of the keys they hold, with no role branch** — `grep -i accountant SearchService.php` finds only prose | Projects, tasks, messages, meetings, people, clients and files are empty because they hold none of those keys; income and expense are full because they hold `finance.view`. **And the Admin finds the books too**, which is the proof it is a capability and not a shell — that line has its own test |
| 10-6 | **A term matching only a restricted record answers `total: 0` with no groups** — the same answer a nonsense term gets | *Homes* matches the client *Buffalo Modular Homes* and nothing else in the database; Tapu gets nothing, with no placeholder row and no count, while a companion test proves the term really does match for the Admin so it cannot quietly stop testing anything. The weaker sibling asserts two searchers' counts differ **and that each response's `total` equals the rows actually in it** — rank-then-filter produces the same rows with a `total` counted before the filter, and that equality is what separates the two |
| 10-7 | **`messages` gets no tsvector — a deliberate deviation from Part D's table list** | `ConversationService::search()` already exists, is already scoped (M-3) and matches with `ILIKE`. Adding the column would put an unused GIN index on the **highest-insert-rate table in the application**, paying write amplification on every message for a read path that does not exist. The column belongs with the conversion, not before it |
| 10-8 | **Message attachments are excluded from file search, with a test pinning it** | A message's reader is decided by `ConversationPolicy` asking the linked task or project over a membership that is **computed rather than stored** — it cannot become a subquery without restating that computation, and an approximation of a membership rule is how a room you cannot enter starts showing its filenames |
| 10-9 | **A Gantt task with no due date is an open-ended mark**: a solid cap on the start date, a tail fading over three days, and the words *"no due date"* beside it | Two of the three options lie. A **one-day bar** (what `TaskCalendar` does) says the work takes a day; it does not, and nobody knows how long it takes, which is the point. A **bar to the window's edge** says it is due at a date that changes when you page the window — worse than wrong, unstable. The first build was 16px and was a speck at a glance, which is the same failure quietly; it was rebuilt at three days with words. Its right handle **adds** a due date, because that is the useful answer to "no due date" |
