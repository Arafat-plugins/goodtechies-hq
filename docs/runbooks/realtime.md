# Runbook: realtime (Reverb), and the polling fallback

Phase 6 gives the application one websocket: **Laravel Reverb**, self-hosted on the same VPS,
started by Supervisor, proxied by Nginx. It carries three channels
(`conversation.{id}`, `notifications.{user_id}`, `task.{id}`) and nothing else.

**It is optional.** Master prompt Part B says a 10–15 second poll is acceptable in the MVP if
Reverb is troublesome, so *polling* is a supported mode and not a broken one. The bell says
which mode it is in, and every payload is the same either way.

---

## The switch is two keys, and they are set together

| | Socket | Polling |
| --- | --- | --- |
| `BROADCAST_CONNECTION` | `reverb` | `log` |
| `VITE_REALTIME` | `reverb` | `polling` |
| `supervisorctl status hq-reverb` | RUNNING | STOPPED |

`BROADCAST_CONNECTION` is how the **server** sends. `VITE_REALTIME` is whether the **browser**
listens, and Vite bakes it into the JavaScript at build time — which is why it lives in `.env`
and not in Admin → Settings (Part D §20 says so in as many words; Settings shows both
read-only).

**Setting one without the other is the one mistake nothing catches for you:**

- `BROADCAST_CONNECTION=reverb` with `VITE_REALTIME=polling` — everything works, nothing is
  live, and Reverb sits there with no subscribers.
- `BROADCAST_CONNECTION=log` with `VITE_REALTIME=reverb` — every browser opens a socket to a
  server that is stopped, the bell shows *"Live updates are reconnecting"* forever, and the
  15-second poll is quietly doing all the work.

Neither is an outage. Both are a line in `.env` and a release.

### Turning the socket on

```bash
cd /var/www/goodtechies-hq
vim .env                       # BROADCAST_CONNECTION=reverb  and  VITE_REALTIME=reverb
                               # REVERB_HOST=<your domain>  REVERB_PORT=443  REVERB_SCHEME=https
SKIP_PULL=1 deploy/deploy.sh   # rebuilds the assets, then starts hq-reverb
```

### Turning it off again (the fallback)

```bash
vim .env                       # BROADCAST_CONNECTION=log  and  VITE_REALTIME=polling
SKIP_PULL=1 deploy/deploy.sh   # rebuilds the assets, then STOPS hq-reverb
```

A `config:clear` is **not** enough for either. `VITE_REALTIME` is inside the compiled bundle,
so the assets have to be rebuilt — which is what `deploy.sh` does, in that order.

## The moving parts

| Piece | Where |
| --- | --- |
| Process | `deploy/supervisor/hq-reverb.conf` → `/etc/supervisor/conf.d/hq-reverb.conf` |
| Command | `php artisan reverb:start --host=127.0.0.1 --port=8080` |
| Websocket URL | `https://<domain>/app/<REVERB_APP_KEY>` → Nginx → `127.0.0.1:8080` |
| Publish API | `https://<domain>/apps/<REVERB_APP_ID>/events` — same proxy |
| Nginx | the two `location ^~ /app/` and `^~ /apps/` blocks in `deploy/nginx.conf` |
| Channel auth | `POST /broadcasting/auth`, `routes/channels.php`, `app/Broadcasting/*` |
| Log | `storage/logs/hq-reverb.log` |
| Credentials | `REVERB_APP_ID` / `_KEY` / `_SECRET` in `.env`, generated by `install.sh` |

Reverb binds to **127.0.0.1 only**, exactly as PostgreSQL and Redis do (Part B §4).
`install.sh` asserts it with the same `assert_local_only` check, and `ufw` opens only 22, 80
and 443. If Reverb ever appears on `0.0.0.0`, that is the bug — not the firewall.

**Realtime needs the queue worker.** Every broadcast is a queued job, deliberately: publishing
is an HTTP call to Reverb, and doing it inline would turn "approve this leave request" into a
500 on a box where Reverb is stopped. So if `hq-queue` is down, nothing is live even when
everything else is right. `supervisorctl status hq-queue` is the first thing to check.

## When the bell is quiet

Work down this list. Each step is one command.

1. **Is the mode what you think it is?**
   `grep -E 'BROADCAST_CONNECTION|VITE_REALTIME' .env`
   If it says polling, the bell is behaving correctly and updates arrive within 15 seconds.

2. **Is the queue worker running?** `supervisorctl status hq-queue`
   A stopped worker means no broadcast ever leaves the application. Notifications are still
   written to the database, so the poll and a page reload both show them.

3. **Is Reverb running?** `supervisorctl status hq-reverb`
   If it is not: `supervisorctl start hq-reverb`, then `tail -n 50 storage/logs/hq-reverb.log`.

4. **Is it listening on the loopback?** `ss -Hltn 'sport = :8080'`
   Expect `127.0.0.1:8080`. Nothing else is correct.

5. **Does Nginx reach it?**
   `curl -si https://<domain>/app/<REVERB_APP_KEY> | head -n 1`
   A **400** or **426** is *success* — that is Reverb refusing a request that is not a
   websocket upgrade. A **502** means Reverb is not running behind the proxy.

6. **Does the browser get authorised?** In the browser's network tab, look at
   `POST /broadcasting/auth`.
   - **200** — subscribed. The problem is further along.
   - **403** — the policy said no. That is the system working: the same person would get a
     404 or a 403 from the HTTP route for the same record. See `app/Broadcasting/`.
   - **302 to /login** — the session expired.

7. **Nothing is wrong but tabs reconnect about once a minute.**
   `proxy_read_timeout` in the two Reverb `location` blocks. It must be comfortably longer
   than Reverb's ping interval (60 s); the shipped value is 3600 s. A 60 s timeout races the
   keep-alive and drops every idle tab, and nothing logs an error when it does.

---

## What the bell does when the socket drops

It does not go quiet, because a bell that has silently stopped being right looks exactly like a
bell with nothing to say.

- The 15-second poll **comes back** for as long as the socket is down, so the badge stays
  correct.
- The popover says *"Live updates are reconnecting. Checking every 15 seconds meanwhile."*
- On reconnect the bell **re-reads once**, because a socket delivers changes and anything that
  happened while it was down was delivered to nobody.
- A deploy restarts Reverb and therefore drops every socket. This is the path that runs every
  release, and it is why it is written down rather than discovered.

## Smoke tests

```bash
deploy/test/run-reverb-test.sh      # Reverb, the templates, and a real websocket. No Docker.
deploy/test/run-install-test.sh     # the whole install on a fresh Ubuntu 24.04 container.
```

`run-reverb-test.sh` starts a real Reverb on a free loopback port, opens a real websocket to
it, publishes a real broadcast through the application and asserts the frame comes back — plus
it checks the rendered Supervisor and Nginx templates for the loopback bind, the upgrade
headers and the read timeout. It needs no Docker and no root, so it is the one to run first.

## What is NOT here

No browser push and no email digests. Both are post-MVP (Part H); the notification engine keeps
a `channels` list per type so they can be added later without a rewrite, and today that list
has exactly one entry.
